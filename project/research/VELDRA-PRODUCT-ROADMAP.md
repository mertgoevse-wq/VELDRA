# VELDRA Product Roadmap — P0-P3

**Loop 20, 2026-08-11.** Synthesizes `VELDRA-ARCHITECTURE-RESEARCH.md`, `VELDRA-REPOSITORY-CANDIDATES.md`, and `VELDRA-DESIGN-SYSTEM.md` into a single prioritized list. Nothing in this document has been implemented — this is the output of a research-only loop, not a sprint plan. Priorities:

- **P0** = necessary for a genuinely functioning VELDRA (gaps, not features — things that are missing, wrong, or unverified today)
- **P1** = high product value, builds directly on what already exists
- **P2** = premium/expansion — real value, but reasonably gated behind a paying tier or a later phase
- **P3** = long-term research direction, not near-term work

Each item states what it builds on (never a parallel system) and which research document it's grounded in.

---

## P0 — Necessary, not optional

1. **Record the verified upstream fork-point.** `stackblitz-labs/bolt.diy @ 2e254ac1` plus the file-count breakdown (306 identical / 84 modified / 93 new / 0 removed, `app/` only) should go into `NOTICE.md` or `BRANDING.md` as a citable, reproducible fact rather than a categorical claim. *(Architecture research §0.5. Trivial, no code risk.)*
2. **Write `project/ARCHITECTURE-ORCHESTRATOR.md`.** `app/lib/orchestrator/types.ts`'s own doc comments reference this file for "rationale and what is deliberately NOT modelled yet" — it doesn't exist. This is a real documentation gap in an already-built system, not new design work. *(Architecture research §0.1.)*
3. **Audit where the 23 providers' API keys actually live today** (localStorage/cookies vs. anything more protected) before any backend/session-persistence work begins, since that work's whole premise (per research §7) is "secrets should never live in localStorage" — confirm the current actual state rather than assuming it either way. *(Architecture research §7 — flagged as not re-checked this loop.)*
4. **Extend `CapabilityKind`** (`registries.ts`) with `'connector'` and `'mcp-server'` values, reusing the existing `DiscoveryState`/`CapabilitySource`/`CapabilityResolver` machinery as-is. This is the single structural gap identified between what the mandate wants (installable agents/skills/tools/connectors/MCP servers) and what already exists (agents/skills/prompt-patterns/methods) — a type-union extension, not a new subsystem. *(Architecture research §2.)*
5. **Add a `PRO` entry to `EntitlementTier`**, distinct from the existing internal-only `DEVELOPER` tier, plus a parallel `capabilities: Set<...>` concept for binary feature flags (local models, extra connectors) that a `Budget` number can't express. This is required before any real FREE/PREMIUM/PRO product surface can exist, and it's an additive change to `entitlement.ts`, not a redesign. *(Architecture research §6.)*
6. **Extend `db.ts`'s IndexedDB schema** with a `Goal`+`Task` object store, so orchestrator state survives a restart — today it only exists in memory. This is the concrete fix for the mandate's "VELDRA darf das ursprüngliche Ziel einer langen Aufgabe nicht verlieren" requirement, using the persistence layer that already works rather than inventing a second one. *(Architecture research §7.)*

## P1 — High product value, builds on what exists

1. **A concrete `AgentRunner` implementation** against the existing `adapters.ts` contract (`AgentInvocation`/`AgentResult`/`ApprovalPort`/`RunStore`), informed by the cross-tool pattern research: isolated-context-window delegation with a merge-back-summary contract (the pattern every real tool researched converges on), Plan/Act-style non-mutating mode as a first-class cheap toggle (maps onto `gauntlet`'s existing `PLANNED`/`RESEARCHING` states), and a repeated-failure circuit breaker (already exists via `MAX_IDENTICAL_FAILURES`/`FailureFingerprint` — just needs a real runner to feed it). *(Architecture research §1, §2.)*
2. **A VELDRA Context Engine, minimum viable slice**: in-process `tree-sitter`/`ts-morph`-based repo map (both real MIT npm packages, no subprocess) + file-relevance scoring feeding what gets included per `Task`, replacing today's implicit full-file-inclusion default. Normalize a `promptCaching` capability field into `ModelCapabilities` (breakpoint count, min tokens, TTL) using the real, verified caching mechanics researched per-provider (Anthropic/OpenAI/Google), so the orchestrator can place stable content ahead of volatile content to maximize cache hits. *(Architecture research §4.)*
3. **MCP server registry entries + a real MCP client hardening pass**: adopt the official TypeScript SDK properly (confirm `mcpService.ts`'s version currency), target Streamable HTTP only (legacy SSE is being actively cut across the industry in 2026), and route every MCP server through the new `DiscoveryState` staging from P0.4 — MCP's own spec explicitly pushes trust decisions onto the client, which is exactly what that staging exists for. *(Architecture research §1.3, §2.)*
4. **"Known vs. discoverable" provider onboarding flow**: a dedicated UI path for VELDRA's existing "openai-like" provider type that attempts live `/v1/models` discovery against a user-entered base URL, falling back to manual entry — this is an unsolved gap industry-wide (confirmed via LibreChat/LiteLLM/an open VS Code issue), not something VELDRA is behind on, and a real differentiator if solved well. *(Architecture research §3.)*
5. **Responsive/UI work continuing Loop 19's pattern**: bottom sheets (not dropdowns/full-screen pushes) for model/provider/skin pickers on mobile — directly actionable from the design-system research and consistent with bugs already found and fixed in Loop 19's own audit. *(Design system §2.3.)*
6. **A distinct, non-generic "AI is working" progress visualization** (the mandate's own cube/pixel-core idea, or a design-owner-approved alternative) instead of defaulting to the now-generic industry shimmer-text pattern — this is a real differentiation opportunity flagged directly by the research (shimmer is now recognized as *the* generic "AI aesthetic," not something distinctive). *(Design system §2.2, §6.)*
7. **High Contrast skin** as the next skin after the already-shipped Obsidian — objectively checkable (WCAG ratios) rather than a subjective mood call, making it tractable without a designer's visual judgment. *(Design system §5.)*
8. **Adopt `Context7` and `Repomix`** (both MIT, both trivially adoptable) as real, immediate wins: Context7 grounds VELDRA's own AI responses in current library docs via MCP; Repomix gives it a working repo-packaging/context tool today, ahead of the custom Context Engine in P1.2. *(Repository candidates §3, §6.)*

## P2 — Premium/expansion

1. **QR-pairing convenience flow** for connecting a local Ollama/LM Studio/llama.cpp server to the Android app (LAN IP + optional key encoded in a QR code) — real, low-risk, well-precedented pattern (ShareRTC on Android). Recommended premium gate: this convenience flow behind PREMIUM/PRO, while manual endpoint entry (base URL + key) stays free for every tier — gates convenience, not capability, avoiding the "artificial limitation" trap. *(Architecture research §5, §6.)*
2. **Local Intelligence Engine, minimum viable**: Gemma 3 270M or 1B via LiteRT/LiteRT-LM (or ExecuTorch once iOS parity matters) as an intent-classification/routing pre-processor in front of the main cloud model — the smallest, most purpose-built, best-verified option found for exactly this role. Gate behind PREMIUM/PRO's "local models" capability flag from P0.5. *(Architecture research §8.)*
3. **`mem0` (Apache-2.0, real TS SDK) for cross-session agent memory**, once a backend exists — the one persistence/memory library found with a directly-integrable TypeScript SDK rather than being reference-only. *(Repository candidates §15.)*
4. **`Stagehand` (MIT) for AI-driven browser automation/E2E**, and `BackstopJS`+`reg-suit` (both MIT) for visual QA — all three are direct, low-risk adoptions that extend VELDRA's existing Playwright investment rather than replacing it; scoped to P2 because they're valuable but not blocking anything in P0/P1. *(Repository candidates §12, §13.)*
5. **`promptfoo` (MIT) in CI** for regression-testing prompts across all 23 LLM providers — genuinely useful, but a testing-infrastructure investment rather than user-facing product value, hence P2 not P1. *(Repository candidates §9.)*
6. **Remaining named skins** (Claude-inspired mood direction, Anthracite, Midnight, Aurora, Ocean, Ember, Forest, Rose, Lavender, Arctic) — real design work requiring product-owner mood/palette decisions per skin, not a batch that should be fabricated at once. Recommend the product owner picks 2-3 to prioritize by name once P1.7 (High Contrast) proves the pattern works for a second, harder skin. *(Design system §5.)*
7. **Full design-token vocabulary beyond color** (font/weight/size/letter-spacing/line-height/radius/border-thickness/shadow/blur/density/animation-speed as user-controllable settings) — the token *categories* are scoped in the design-system doc, but sizing and building the actual settings UI is real, non-trivial work belonging here, not P1. *(Design system §4.)*

## P3 — Long-term research direction, not near-term work

1. **Audio/music intelligence** — per the mandate's own instruction not to over-invest here yet. When it becomes active: Demucs-class stem separation via the actively-maintained `python-audio-separator` wrapper (MIT), librosa (ISC) for general audio analysis, CLAP/LAION-CLAP-Music (CC0) for audio embeddings. **Hard exclude**: Essentia/essentia.js (AGPL-3.0) and madmom's bundled models (CC-BY-NC-SA) — both are commercial-use blockers as-is, flagged clearly so a future loop doesn't reach for the technically-most-convenient option and hit a license wall. FFmpeg's own license is a **build-configuration decision** (LGPL-only vs. GPL-triggering flags) that must be explicitly controlled whenever a bundled FFmpeg binary is chosen for the Android app. *(Architecture research §9, Repository candidates §17-18.)*
2. **Broader local-model-format support beyond the P2 minimum** (ONNX Runtime for Phi-3/4-mini-class models if a genuinely capable *offline* assistant becomes a goal, not just a lightweight router; MLX once its iOS story is independently confirmed against Apple's own docs, not just secondary sources). *(Architecture research §8.1.)*
3. **Full WebRTC device-to-device transfer** (not just QR-encoded server pairing from P2.1) — real pattern exists (ShareRTC-style SDP-via-QR handshake) but is a materially bigger feature than server pairing, and the mandate itself frames Bluetooth/WebRTC as the last, most experimental item in its own connection-methods list. *(Architecture research §5.)*
4. **Agent-orchestration frameworks as actual dependencies** (VoltAgent, LangGraph.js) if VELDRA's own `AgentRunner` (P1.1) turns out to need more graph/workflow machinery than a bespoke implementation can reasonably cover — evaluate only after the bespoke version proves insufficient, not preemptively. *(Repository candidates §1.)*
5. **iOS platform work generally** — every "verified Android, iOs unconfirmed" flag in the architecture research (MLX, LiteRT-LM) should be resolved with primary-source verification before any iOS-specific commitment is made; ExecuTorch is currently the strongest cross-platform (Android+iOS) evidence found and should be the reference point if/when iOS work starts. *(Architecture research §8.1, §11.)*
